# Deployment and recovery contract

Workflow owns db/ and deploy/compose.yml. PostgreSQL bootstrap belongs to HU-INF-02 and must create a restricted LOGIN workflow_app. Workflow never creates a database instance or an application login. Shared PostgreSQL DNS is synkro-db on the external platform network; HTTP remains internal port 8080.

## Preparation

Provide protected absolute paths WORKFLOW_APP_PASSWORD_PATH and JWT_PUBLIC_KEY_PATH, WORKFLOW_SERVICE_TOKEN, and PLATFORM_NETWORK. The token is issued by Auth with SERVICE role and customers:read, stock:reserve, stock:release, sales:register permissions. Never use a human token for participant calls. The mounted key is Auth's public key only. Application credentials are workflow_app and its password file. FLYWAY_URL, FLYWAY_USER and FLYWAY_PASSWORD are administrator inputs used only by the tooling runner.

Run the owning Compose workflow-db-migrate service under the tooling profile, then start synkro-workflow. Runner mounts db/ read-only, uses Flyway 11.20.3, sets only/default/history schema workflow_schema, validates checksums and has five bounded connection retries. No database port is published. Automatic Spring/Flyway/SQL migrations are disabled. Compose evaluates both services, so migration-only callers must still supply valid placeholder application paths and a nonempty placeholder service token; these inputs are not passed to the runner.

The application requires a valid RSA public key (at least 2048 bits) at startup. Health queries the owning saga table with application permissions; it returns 503 when the store is unavailable. Participant health does not determine store health.

## Execution limits

Four workers and 64 queued IDs are defaults. Configuration allows 1–16 workers, 1–1000 queued IDs, and a 100–60000 ms scan interval. Hikari has 12 connections; JDBC acquisition is bounded to 3 seconds. Every participant connection is bounded to 2 seconds and each full response to 3 seconds with a 1 MiB maximum body. Only classified transient transport I/O or request timeouts and HTTP 429/500/502/503/504 receive at most three persisted attempts, with exponential full-jitter backoff (wait drawn from 0..min(2000, 100<<(attempt-1)) ms). HU-WKF-04 removed 408 and replaced the historical bound+random(0..bound/2) wait (historical, retained for attribution: it was the delivered behavior until then). Business rejection and authorization rejection are not retried as transient failures.

The HTTP response deadline defaults to 1000 ms and allows 1–10000 ms. Deadline expiry returns the stored RUNNING resource; it does not cancel execution. A full queue leaves the created row durable for the independent scanner. GET and duplicate POST do not launch competing workers. Shutdown stops scanning, drains workers for five seconds, then interrupts and waits at most three more seconds. Startup scans durable RUNNING rows immediately.

## Ownership and crash recovery

A dedicated PostgreSQL connection holds a two-integer session advisory lock for the saga UUID across committed intent/result writes. Since HU-WKF-04 the key is first 0x57464C4B (WFLK, 1464224843) and second the XOR of the UUID's four signed 32-bit words (Auth refresh keeps 0x52544F4B; Auth initialization uses the bigint overload). The legacy pair used the same first-key space without a reserved first key; no schema change is involved.

### Advisory-key algorithm switch (planned, NOT executed)

Old and new algorithms must never run together, otherwise two executors could lock the same saga under different keys. Procedure (it is a documented plan; record who executed it and when only after it is actually carried out):

1. Stop every legacy executor (all Workflow replicas, including scanners). Do not start a new-algorithm instance yet.
2. Confirm no ownership remains: `SELECT l.pid,l.classid,l.objid FROM pg_catalog.pg_locks l JOIN pg_catalog.pg_stat_activity a USING (pid) WHERE l.locktype='advisory' AND l.objsubid=2 AND l.granted AND a.application_name='synkro-workflow-owner';` must return no held Workflow lock. Query with the authorized operator role after every executor has stopped; wait for the bounded old sessions or terminate only those sessions through the reviewed operator route.
3. Start only new-algorithm executors and verify there is one algorithm in the fleet (image/revision identical on every replica) before routing traffic.
4. Rollback uses the same rule in reverse: stop all new-algorithm executors, confirm no advisory ownership remains, then start only legacy executors. Never run a mixed fleet, even briefly, and never during an active execution window.

Execution record: not executed. Executor / date: pending. The same connection performs every update. It never reconnects a lease. Successful commits preserve the lock; explicit unlock occurs before pooled return. Failed unlock aborts the connection. PostgreSQL releases ownership after process/connection death or the 15-second idle session bound. A terminated old connection cannot overwrite a successor.

RUNNING with no failed_step resumes forward execution; RUNNING with failed_step resumes compensation. The private step_results execution object retains the first correlation ID, pending effect and attempt count. Persisted pending effects replay the exact stable sagaId:step participant idempotency key. Successful results commit before the next external step. Release reads the original reservation first and accepts an already released result.

A successful external effect followed by failed local persistence is recovered by replaying the owning operation, never by guessing that it did not happen. A lost Sales response must not release stock. An ambiguous operation that exhausts its attempt budget remains RUNNING with private OUTCOME_UNRESOLVED and is excluded from automated scanning. This is durable operational suspension, not a terminal success. It requires participant evidence and a reviewed recovery decision. Do not reset its budget or change rows ad hoc. FAILED compensation is terminal and has no automatic repair endpoint.

## Operational evidence and rollback

Use read-only administrator inspection in a protected session to identify saga_id, failed_step, completed_steps and sanitized internal error codes. Do not export input, step_results, SQL connection diagnostics or credentials to API clients or ordinary logs. Retain the original correlation ID for participant-owner investigation.

For unresolved Sales, clearing evidence is the participant's idempotent result for the original key, including customer, frozen lines and createdBy. If that result cannot be established, keep the reservation and escalate to Sales/architecture review. Changing recovery policy, resetting attempts or adding a repair interface needs a published design review. Exhausted compensation similarly requires an owner-reviewed operational decision.

U scripts are a controlled rollback family outside forward discovery. Destructive rollback/rebuild is demonstrated only on disposable databases: execute U005 through U002 in reverse order, deliberately remove that disposable schema's Flyway history, then U001; recreate with the owning runner. Never change an applied V migration, run clean, repair checksum drift automatically, or run these disposable steps against a shared environment. Shared rollback requires backup and explicit review.

## Evidence separation

mvn verify, tests/check_coverage.py and tests/test_deployment.py need only this repository. tests/process_acceptance.py requires Docker and cryptography 46.0.3 and runs real PostgreSQL/Workflow processes with controlled participants. tests/hybrid_acceptance.py is local-only and requires clean immutable snapshots of the exact participant pins embedded in that script. It builds real Customers, Products and Sales plus owning Products/Sales migration runners, but it still asserts the historical Customers 501 and uses a controlled Customers fixture. Controlled and hybrid evidence never constitute fully real acceptance. tests/real_services_acceptance.py (HU-WKF-04) is the real-services harness: exact `--pin` SHAs for six clean snapshots, no fixture participant, normal completion, confirmed-rejection compensation, protected tokens, stable keys/traces and owned cleanup. Its executed local results, exact snapshots and remaining gates are recorded in execution-report.md.

Confirmed rejection requires the owning operation's published status AND a valid shared Error envelope: Customers lookup 404; reservation creation and Sales registration 400/422; reservation read/release 404. The response must be application/json, a single JSON object without duplicate fields/trailing JSON, with textual error/message/traceId, the original request correlation, and valid field/message details when supplied. Status 400 accepts VALIDATION_ERROR, 404 NOT_FOUND, and 422 BUSINESS_RULE_VIOLATION or INVALID_STATUS_TRANSITION. A missing, malformed or contradictory envelope is INVALID_RESPONSE, never evidence that Sales did not commit; retain its reservation and RUNNING/OUTCOME_UNRESOLVED without retrying a contract failure.

Only HTTP 429/500/502/503/504, a bounded request wait timeout, and an allow-list of asynchronous transport failures (HTTP/socket timeouts, EOF, socket resets/connection refusal, closed channel) permit bounded retry; any other IOException is LOCAL_FAILURE, not a blind retry. HTTP 408 is not adopted (historical: the earlier delivery retried it). Protocol violations and the 1 MiB response limit are INVALID_RESPONSE. TLS/hostname configuration failures, invalid URI/header configuration, serialization, unexpected programming failures, cancellation and interruption are non-retryable LOCAL_FAILURE; interruption preserves the thread flag. Serialization/configuration errors occur before sending and cannot be mistaken for transport failures. LOCAL_FAILURE is an internal port classification, with no new stored/public status, schema or endpoint. Neither local failures nor authorization failures confirm a rejected sale. No exception message, response body, URL or credential is copied to diagnostics or the public error envelope.

Structural 501 and undocumented statuses are not transient retries or proof of a failed sale. Unknown Sales 4xx, including 408, is INVALID_RESPONSE and preserves RUNNING/OUTCOME_UNRESOLVED without automatic retry; retain the original key and obtain participant evidence through the reviewed investigation procedure.

## Circuit breaker (HU-WKF-04)

One process-local breaker per participant wraps the participant port: Customers, Products (shared by reserve-stock and release-stock) and Sales; failure threshold 3 consecutive transient failures, cooldown 15 s, exactly one HALF_OPEN probe. Only classified transient failures count; only a fully validated successful result closes/resets; business rejections, authorization, local and contract failures are neutral and free the probe. An open circuit fails fast without any network call as CIRCUIT_OPEN: it is not a rejection and not evidence that an earlier write did not commit, so it never starts or completes compensation. Conservative resolution of the design's open question (no endpoint, no budget redefinition): the attempt was already persisted before the adapter was reached, so a fail-fast refusal consumes one local attempt; a forward step then stays RUNNING with private OUTCOME_UNRESOLVED and is excluded from startup scanning (no retry loop, no budget replenishment). A refusal during release-stock never reports successful compensation; with the existing non-transient release path it ends FAILED with the reservation retained. Reviewers may prefer a different outcome for release-stock; that needs explicit consent. Permit generations prevent delayed outcomes from an earlier circuit cycle from changing a recovered cycle. State is not stored, not projected and logs nothing. The call timeout stays the documented composition override (3 s response, 2 s connect), not the guide's 5 s table value. Fixing a local configuration or participant contract does not automatically reset suspended attempts or release stock; follow the owner-reviewed investigation procedure above.
